Для этой спецификации я бы определил приёмку как проверку **фактического поведения развёрнутой системы**, а не просто наличие нужных параметров в исходниках и конфигурационных файлах.

Изменения можно считать принятыми, только если одновременно выполнены три условия:

- Все требования реализованы.
- Сценарии из спецификации проходят на работающем стенде.
- Негативные проверки подтверждают, что обход аутентификации и сетевых ограничений невозможен в предусмотренной модели угроз.

Ниже — предлагаемый набор критериев приёмки (Acceptance Criteria).

## **1. Критерии приёмки по направлениям**

### **A. Безопасность Pad и OIDC**

Блокирующие критерии

| ID      | Критерий приёмки                                              | Как проверять                                                                   |
| ------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| AUTH-01 | CORS разрешает только `FRONTEND_URL`                          | Запрос с разрешённого origin получает корректный `Access-Control-Allow-Origin`  |
| AUTH-02 | CORS не отражает произвольный Origin                          | Запросы с посторонних доменов не получают разрешение, в том числе с credentials |
| AUTH-03 | OIDC `state` генерируется криптографически случайным          | Проверить реализацию генерации и хранения на сервере                            |
| AUTH-04 | `state` одноразовый                                           | Повторный callback с уже использованным значением отклоняется                   |
| AUTH-05 | Callback без `state` или с неправильным значением отклоняется | Негативные интеграционные тесты                                                 |
| AUTH-06 | После входа создаётся новый session ID                        | Сравнить идентификатор до и после авторизации                                   |
| AUTH-07 | Старая pre-auth сессия становится недействительной            | Повторно отправить старую cookie и получить отказ                               |
| AUTH-08 | Cookie содержит `Secure`, `HttpOnly`, `SameSite=Lax`          | Проверить `Set-Cookie`                                                          |
| AUTH-09 | Cookie содержит только непрозрачный идентификатор             | Проверить, что access/refresh tokens отсутствуют в cookie                       |
| AUTH-10 | Logout удаляет серверную сессию и очищает cookie              | Повторить запрос со старой cookie после выхода                                  |
| AUTH-11 | Forwarded-заголовки доверяются только от Caddy                | Прямой запрос с поддельным `X-Forwarded-Proto` не меняет определение схемы      |
| AUTH-12 | Вход использует точные redirect URI                           | Проверить конфигурацию клиентов Keycloak и отказ на незарегистрированных URI    |

Дополнительно необходимо проверить:

- Срок жизни сессии и refresh token.
- Поведение при истечении access token.
- Поведение при истечении refresh token.
- Поведение при недоступности Keycloak.
- Отсутствие токенов и секретов в логах.
- Защиту от CSRF для изменяющих состояние запросов.

Последний пункт стоит явно добавить в спецификацию: `SameSite=Lax` и ограниченный CORS сами по себе не заменяют полноценную CSRF-защиту.

### **B. Единая аутентификация через Caddy**

| ID       | Критерий приёмки                                                | Как проверять                                                   |
| -------- | --------------------------------------------------------------- | --------------------------------------------------------------- |

| PROXY-02 | Coder требует авторизации                                       | Открыть Coder без cookie                                        |

| PROXY-06 | Неавторизованный браузер перенаправляется на login              | Проверить `Location` и сохранение исходного пути                |
| PROXY-07 | API получает `401`, а не HTML redirect                          | Запросить защищённый endpoint с `Accept: application/json`      |

## **2. Сквозные сценарии приёмки**

Отдельные тесты компонентов необходимы, но главная проверка — прохождение полного пользовательского сценария.

**Сценарий 1. Первый вход пользователя**

1. Пользователь открывает `https://pad.example.com` без cookie.
2. Caddy перенаправляет его на Pad login.
3. Pad создаёт OIDC authorization request с `state`.
4. Keycloak аутентифицирует пользователя.
5. Pad проверяет `state`, обменивает code и создаёт новую сессию.
6. Браузер получает защищённую cookie.
7. Пользователь возвращается на исходный Pad URL.

Ожидаемый результат: успешный вход

**Сценарий 2. Доступ к Coder**

1. Авторизованный пользователь открывает `https://coder.example.com`.
2. Браузер отправляет общую session cookie.
3. Caddy проверяет её через Pad.
4. Pad подтверждает действительность сессии.
5. Caddy пропускает запрос в Coder.
6. Пользователь открывает workspace и терминал.

Ожидаемый результат: Coder доступен, WebSocket работает

**Сценарий 3. Отзыв доступа**

1. Пользователь авторизован в Pad и Coder.
2. Администратор удаляет его серверную сессию.
3. Пользователь повторно обращается к Coder.
4. Caddy получает отказ от Pad verification.

Ожидаемый результат: повторный доступ запрещён

**Сценарий 4. Отказ инфраструктуры**

1. Пользователь имеет действующую cookie.
2. Pad становится недоступен.
3. Пользователь обращается к защищённому Coder endpoint.
4. Caddy не может проверить сессию.

Ожидаемый результат: 502/503, доступ не предоставляется

## **3. Требования к тестированию**

Я бы потребовал от разработчика следующие уровни тестирования:

| Уровень           | Что проверяется                                               | Обязательность |
| ----------------- | ------------------------------------------------------------- | -------------- |
| Unit tests        | Генерация и проверка state, сессии, redirect validation, роли | Обязательно    |
| Integration tests | Pad + PostgreSQL + Redis + Keycloak                           | Обязательно    |
| Proxy tests       | Caddy + Pad verification + cookie forwarding                  | Обязательно    |
| E2E tests         | Полный вход, Pad, Coder, logout                               | Обязательно    |
| Security tests    | CORS, CSRF, spoofing headers, open redirect, session replay   | Обязательно    |
| Deployment tests  | Чистая установка, restart, backup/restore                     | Обязательно    |
| Network tests     | Недоступность внутренних портов извне                         | Обязательно    |

Особенно важно проводить E2E-тесты именно через Caddy, а не обращаться к Pad напрямую. Иначе можно получить ситуацию, когда приложение работает, но reverse proxy неправильно обрабатывает авторизацию.

## **5. Что я бы дополнительно уточнил в самой спецификации**

Есть несколько мест, которые пока недостаточно определены для однозначной приёмки.

| Вопрос             | Что нужно зафиксировать                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------- |
| Общая cookie       | Какой именно `COOKIE_DOMAIN`, `Path` и поведение при отсутствии общего родительского домена |
| Refresh            | Как Caddy передаёт обновлённый `Set-Cookie` от `/api/auth/verify` браузеру                  |
| CSRF               | Какая конкретно защита применяется для изменяющих состояние запросов                        |
| WebSocket          | Что происходит с уже открытым соединением после отзыва сессии                               |
| Rate limiting      | Лимиты на login, callback и API                                                             |
| Backup             | Периодичность, срок хранения и проверка целостности                                         |
| Secrets            | Где хранятся секреты и как выполняется их ротация                                           |
| Admin IP allowlist | Как обрабатываются IPv4, IPv6 и доверенные proxy                                            |
| Мониторинг         | Как оператор узнаёт о недоступности сервиса, БД или проблемах с сертификатами               |

Есть и более тонкий момент: проверка сессии на каждом HTTP-запросе не гарантирует немедленного закрытия уже установленного WebSocket-соединения. Если требуется немедленный отзыв доступа, это должно быть отдельным требованием.
