Для минимально безопасной версии Pad.ws я бы разделил работу на две части: **доработка самого проекта** и **подготовка серверной инфраструктуры**.

Цель — не построить идеальную production-платформу, а получить версию, которую можно безопасно развернуть на собственном VPS и предоставить ограниченному кругу пользователей.

## **1. Что нужно доработать в Pad.ws**

| Приоритет   | Что сделать                                          | Зачем                                                        |
| ----------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| Критический | Защитить API и проверить авторизацию каждого запроса | Чтобы пользователь не мог получить чужие данные              |
| Критический | Ограничить доступ к Coder и Keycloak                 | Не выставлять административные интерфейсы всему интернету    |
| Критический | Защитить Docker Socket и права Coder                 | Workspace потенциально может получить доступ к хосту         |
| Критический | Убрать тестовые пароли и секреты из конфигурации     | Исключить компрометацию сервисов                             |
| Высокий     | Настроить HTTPS и корректные OIDC Redirect URI       | Защитить вход и передачу токенов                             |
| Высокий     | Изолировать рабочие окружения пользователей          | Не допустить доступа одного пользователя к окружению другого |
| Высокий     | Настроить ограничения CPU, RAM и диска               | Защититься от чрезмерного потребления ресурсов               |
| Средний     | Настроить резервное копирование PostgreSQL           | Сохранить пользователей и данные                             |
| Средний     | Добавить мониторинг и журналирование                 | Обнаруживать ошибки и подозрительную активность              |

Особенно внимательно нужно проверить **изоляцию Workspace**. Coder управляет удалёнными окружениями, поэтому недостаточно просто закрыть его веб-интерфейс паролем.

## **2. Что потребуется для развёртывания**

Для одного VPS с небольшим количеством пользователей:

| Компонент  | Что потребуется                                                           |
| ---------- | ------------------------------------------------------------------------- |
| Сервер     | Debian/Ubuntu, желательно от 4 CPU и 8 GB RAM для начального тестирования |
| Docker     | Docker Engine и Docker Compose                                            |
| Pad.ws     | Само приложение и FastAPI backend                                         |
| PostgreSQL | Постоянное хранилище данных                                               |
| Redis      | Кэш и сессии                                                              |
| Keycloak   | Авторизация через OIDC                                                    |
| Coder      | Управление Workspace                                                      |
| Caddy      | HTTPS и reverse proxy                                                     |
| Домен      | Домен и DNS-записи для сервисов                                           |

4 CPU и 8 GB RAM — ориентир для небольшого тестового развёртывания, а не гарантированная производительность. Ресурсы самих Workspace нужно считать отдельно.

### **Пример DNS**

Можно использовать один домен и три поддомена:

```
pad.example.com      → Pad.ws
auth.example.com     → Keycloak
coder.example.com    → Coder
```

Все три записи могут указывать на один IP-адрес VPS. Caddy будет направлять запросы к нужным контейнерам.

## **3. Последовательность развёртывания**

1. Подготовить Debian, Docker и Compose.
2. Настроить DNS и Caddy.
3. Запустить PostgreSQL и Redis.
4. Запустить Keycloak и настроить Realm, Client, OIDC.
5. Запустить Coder и создать Template для Workspace.
6. Настроить Pad: API Key Coder, Template ID, Organization ID, адреса и секреты.
7. Запустить Pad.ws.
8. Проверить авторизацию, изоляцию пользователей и работу Workspace.
9. Настроить резервное копирование и мониторинг.

Основа этой последовательности соответствует официальной инструкции проекта.&#x20;

## **4. Самые важные изменения перед публичным запуском**

Я бы выделил пять обязательных задач:

1. **Сетевая архитектура:** отказаться от небезопасного выставления всех сервисов через host networking; оставить публичными только необходимые HTTP/HTTPS endpoints.
2. **Coder и Docker:** разобраться с доступом к Docker Socket. Не предоставлять пользовательским Workspace привилегии хоста.
3. **Авторизация:** убрать `*` из разрешённых Redirect URI, настроить точные адреса и проверить права на API.
4. **Изоляция:** убедиться, что пользователи не могут просматривать чужие доски, терминалы и Workspace.
5. **Секреты:** заменить все тестовые значения, защитить `.env`, ограничить доступ к административным панелям.

Отдельно стоит учитывать, что у оригинального проекта пока нет подтверждённого production-ready сценария self-hosting.&#x20;
